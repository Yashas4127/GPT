## 2.2 Architecture and request flow

A typical layered design is:

``` text
React UI
   |
   | HTTP request (JSON)
   v
Express routes
   |
   v
Authentication / validation middleware
   |
   v
Controller
   |
   v
Service / business logic
   |
   v
MongoDB data access
   |
   v
JSON response
   |
   v
React UI update
```

**Frontend:** displays forms, account details, transaction history and
feedback.

**Route:** maps an HTTP method and URL to a controller.

**Middleware:** performs cross-cutting work such as authentication,
validation, logging and error handling.

**Controller:** reads request data, calls business logic and returns an
HTTP response.

**Service:** contains business rules, such as checking whether a
transfer is allowed.

**Database layer:** reads and writes persistent data.

**Why separate these layers?** Separation makes code easier to test,
maintain and change. Controllers should not become huge files containing
all business logic.

## 2.3 REST API fundamentals

REST is an architectural style for designing networked APIs around
resources.

Typical methods:

  Method   Common purpose                    Example
  -------- --------------------------------- -----------------------------
  GET      Read data                         `GET /accounts/:id`
  POST     Create or initiate an operation   `POST /transactions`
  PUT      Replace a resource                `PUT /users/:id`
  PATCH    Partially update a resource       `PATCH /users/:id`
  DELETE   Delete a resource                 `DELETE /beneficiaries/:id`

A REST API commonly uses JSON request and response bodies.

Important HTTP status codes:

  Code   Meaning
  ------ -------------------------------------------
  200    OK
  201    Created
  204    Successful, no response body
  400    Bad request / invalid input
  401    Not authenticated
  403    Authenticated but not allowed
  404    Resource not found
  409    Conflict, such as a duplicate operation
  422    Semantically invalid input (usage varies)
  429    Too many requests
  500    Internal server error

**Q: PUT vs PATCH?**\
A: PUT generally replaces the resource representation; PATCH applies a
partial update. Exact API semantics depend on the design.

**Q: GET vs POST?**\
A: GET retrieves data and should be safe/read-only. POST submits data
and commonly creates a resource or triggers an operation.

## 2.4 JWT authentication

JWT means JSON Web Token. It is a compact, signed token format commonly
used to carry claims between a client and server.

A JWT has three Base64URL-encoded parts:

``` text
header.payload.signature
```

-   Header: token type and signing algorithm.
-   Payload: claims such as user ID and expiry.
-   Signature: helps the server verify that the token was not modified.

Typical login flow:

``` text
User submits credentials
        |
        v
Server validates credentials
        |
        v
Server creates signed JWT
        |
        v
Client receives token
        |
        v
Client sends token with later request
        |
        v
Authentication middleware verifies token
        |
        v
Protected route continues or returns 401
```

**Q: Is JWT encrypted?**\
A: A normal signed JWT is not encrypted. Its payload can be decoded, so
secrets and passwords must never be placed in it. The signature protects
integrity, not confidentiality.

**Q: Authentication vs authorization?**\
A: Authentication answers "Who are you?" Authorization answers "What are
you allowed to do?"

**Q: What is middleware?**\
A: Middleware is a function that runs during the request-response cycle.
In Express it can inspect or modify the request/response, end the
response, or call `next()` to pass control onward.

**Q: How should passwords be stored?**\
A: Store a password hash created with a password-hashing algorithm such
as bcrypt or Argon2, with appropriate parameters. Do not store plaintext
passwords or use ordinary fast hashes such as plain SHA-256 for password
storage.

**Q: Where should tokens be stored?**\
A: This depends on the threat model. Secure, HttpOnly, SameSite cookies
can reduce exposure to JavaScript-based token theft, but require CSRF
considerations. Browser storage is convenient but exposed to successful
XSS. Explain the actual choice your application makes and its
trade-offs.

## 2.5 Banking transactions, ledger and consistency

A transfer is not merely "subtract from one account and add to another."
Both changes must succeed together.

Conceptual transfer:

``` text
1. Authenticate the user.
2. Validate source account, destination account and amount.
3. Check authorization and available balance.
4. Begin database transaction.
5. Debit source account.
6. Credit destination account.
7. Record transaction/ledger entries.
8. Commit transaction.
9. Return success.
```

If any step fails before commit, roll back the transaction.

**Q: What is a database transaction?**\
A: A group of database operations treated as one logical unit. It either
commits successfully or is rolled back, according to the database's
transaction semantics.

**Q: What are ACID properties?** - Atomicity: all operations succeed or
none do. - Consistency: constraints and invariants remain valid. -
Isolation: concurrent transactions do not produce unacceptable
interference. - Durability: committed changes survive failures, subject
to database guarantees.

**Q: What is a ledger?**\
A: A ledger is an auditable record of financial movements. A common
design records debit and credit entries for a transfer rather than
relying only on a mutable balance field. The exact design depends on the
system.

**Q: Why keep a ledger if an account has a balance?**\
A: A balance is the current summary. A ledger provides the history
explaining how the balance changed, supports reconciliation and audit,
and helps investigate errors.

**Q: What happens if money is debited but not credited?**\
A: The debit and credit should be part of one atomic database
transaction where supported. If operations cross independent systems,
use a carefully designed distributed workflow, idempotency and
compensating actions rather than assuming a single database transaction
covers everything.

**Q: What is a race condition?**\
A: A result depends on the timing/interleaving of concurrent operations.
For example, two withdrawals can both read the same old balance and both
approve unless updates are protected.

**Q: How can you prevent an overdraft under concurrent withdrawals?**\
A: Use an atomic conditional update or transaction with appropriate
isolation/locking. For example, update the balance only when the current
balance is at least the withdrawal amount, and check that exactly one
row/document was modified. The exact technique depends on the database
and schema.

**Q: What is idempotency?**\
A: An operation is idempotent if repeating the same request has the same
effect as performing it once. For payments, a client can send an
idempotency key; the server stores the key and result so retries do not
create duplicate transfers.

**Q: How do you prevent duplicate transactions?**\
A: Validate requests, use a unique idempotency key with a database
uniqueness constraint, and make the transaction operation atomic. Do not
rely only on disabling a frontend button.

**Q: What if the client times out after the server committed the
transfer?**\
A: The client may retry. An idempotency key lets the server return the
original result instead of performing the transfer again.

**Important MongoDB note:** Multi-document ACID transactions are
supported in appropriate MongoDB deployment configurations, but they are
not automatically available in every standalone local setup. Know
whether your project uses a replica set/transaction-capable setup. Never
claim transaction guarantees you have not tested.

## 2.6 MongoDB data modelling questions

**Q: What is MongoDB?**\
A: A document-oriented NoSQL database. Data is stored in BSON documents,
commonly grouped into collections.

**Q: SQL vs NoSQL?**\
A: Relational databases organize data into tables with defined
relationships and strong SQL querying. Document databases store flexible
documents and can be useful when data naturally fits document
structures. The choice depends on relationships, consistency needs,
query patterns and operational requirements---not simply "NoSQL is
faster."

**Q: Embed or reference?**\
A: Embed related data when it is commonly read together and bounded in
size. Reference separate documents when data is shared, independently
updated, or can grow without bound.

**Q: What is an index?**\
A: A data structure that helps the database find records more
efficiently for selected query patterns. Indexes speed up reads but
consume storage and add write/update overhead.

**Q: What is aggregation?**\
A: MongoDB's aggregation pipeline processes documents through stages
such as `$match`, `$group`, `$project` and `$sort` to transform and
summarize data.

## 3.1 What is Artificial Intelligence, Machine Learning and Deep Learning?

    than relying only on hand-written rules.
-   Deep Learning: ML using neural networks with multiple layers.
-   Generative AI: models that generate new content such as text,

-   LLM: a large language model trained to process and generate

``` text
        |
        +--- Machine Learning
                 |

                          |

```

Not every AI system is an LLM, and not every ML model is generative.

## 3.2 What is an LLM?

LLM means Large Language Model. It is trained on large text corpora to
model language and generate likely token sequences.

Examples include GPT, Gemini, Claude, Llama and Mistral.

A token is a unit of text used by the model. It can be a whole word,
part of a word, punctuation or another text unit.

**Q: How does an LLM generate text?**\
A: In simplified terms, it converts input into tokens, processes them
through a neural network and predicts a probability distribution for the
next token. It selects a token according to its decoding configuration
and repeats this process to generate a response.

**Q: What is a context window?**\
A: The maximum amount of input and generated tokens a model can process
in one request. A large context window does not mean the model remembers
everything permanently.

**Q: What is temperature?**\
A: A decoding parameter that influences randomness in token selection.
Lower temperature usually produces more predictable output; higher
temperature allows more variation. It does not make the model more
knowledgeable.

**Q: What is a hallucination?**\
A: A generated claim that sounds plausible but is false, unsupported or
fabricated.

**Q: How can hallucinations be reduced?**\
A: Ground answers in trusted retrieved context, provide clear
instructions, require citations or structured evidence where possible,
validate outputs, use tools for facts that need checking and allow the
system to say it does not know. These methods reduce risk but do not
guarantee zero hallucinations.

## 3.3 LLM vs chatbot vs AI agent

-   LLM: the model that processes and generates language.
-   Chatbot: an application/interface for conversation. It may be
    rule-based or LLM-powered.
-   AI agent: a system that uses a model and other components to choose
    actions, use tools, observe results and work toward a goal.

Example: - Chatbot: answers "How do I check my order?" - Tool-using
agent: calls an order API, checks the order status and returns the
result.

An agent is not necessarily fully autonomous. It can require human
approval or operate under strict rules.

## 3.4 What is prompt engineering?

Prompt engineering means designing instructions and context to guide
model output.

A good prompt can specify: - Role or task. - Relevant context. -
Constraints. - Expected output format. - What to do when information is
missing. - Examples of desired output.

Example:

``` text
You are a support assistant.
Answer only using the supplied policy context.
If the context does not contain the answer, say you do not know.
Return:
1. Answer
2. Supporting policy section
```

A prompt is not a security boundary. Validate outputs and enforce
permissions in application code.

## 3.5 What is tool/function calling?

Tool calling lets a model request that the application execute a
predefined function with structured arguments.

Example flow:

``` text
User: What is the status of order 123?
             |
             v
          LLM model
             |
             v
Model requests: get_order_status(order_id=123)
             |
             v
Application validates arguments and permissions
             |
             v
Application calls order API/database
             |
             v
Tool result returned to model
             |
             v
Model generates user-facing answer
```

Important: the model does not magically execute arbitrary code. The
application defines available tools and decides whether/how to execute
requested calls.

**Q: Why validate tool arguments?**\
A: The model may generate missing, malformed or unsafe arguments.
Validate types, ranges, permissions and business rules before executing
a tool.

**Q: What is the risk of giving an agent tools?**\
A: It can perform unintended actions, leak data or misuse permissions if
tools are too powerful. Use least privilege, allowlists, validation,
approval for sensitive actions, audit logs, timeouts and rate limits.

## 3.6 What is RAG (Retrieval-Augmented Generation)?

RAG connects an LLM to external information at answer time.

Why use it? - The model may not know private company documents. -
Information may change after the model was trained. - Answers should be
grounded in a selected knowledge source. - It can avoid fine-tuning for
every document update.

### RAG ingestion pipeline

``` text
Documents (PDF / DOCX / HTML)
          |
          v
      Text extraction
          |
          v
       Chunking
          |
          v
  Embedding model converts
  chunks into vectors
          |
          v
 Vector database / index
```

### RAG query pipeline

``` text
User question
     |
     v
Question embedding
     |
     v
Similarity / hybrid retrieval
     |
     v
Relevant chunks + metadata
     |
     v
Prompt with retrieved context
     |
     v
LLM generates grounded answer
```

**Chunking:** splitting long content into smaller passages. Chunk size
and overlap affect retrieval quality.

**Embedding:** a numerical vector representing semantic information in
text. Similar meanings often have vectors that are close under a chosen
distance/similarity measure.

**Vector database:** stores vectors and supports similarity search,
often with metadata filtering.

Examples: FAISS, Chroma, Qdrant, Pinecone and other vector search
systems.

**Similarity search:** finds vectors close to a query vector using a
metric such as cosine similarity or distance.

**Metadata filtering:** restricts retrieval to documents or chunks
matching fields such as tenant, document type or access permissions.

**Q: Does RAG train the LLM?**\
A: No. Standard RAG retrieves external content and includes it in the
model's context at inference time. It does not update the model's
weights.

**Q: RAG vs fine-tuning?**\
A: RAG is generally useful for providing current or private reference
information. Fine-tuning changes model parameters to adapt behaviour,
style or task performance. They solve different problems and can be
combined.

**Q: What can go wrong in RAG?**\
A: Poor document extraction, bad chunk boundaries, weak embeddings,
irrelevant retrieval, stale documents, missing access filters, context
overflow and the model ignoring or misinterpreting retrieved content.

**Q: How can RAG quality be improved?**\
A: Improve parsing and chunking, choose an appropriate embedding model,
use metadata filters, hybrid search or reranking where useful, evaluate
retrieval separately from answer quality, and keep the knowledge base
updated.

## 3.7 LangChain

It provides integrations and abstractions for: - Chat models. - Prompt
templates. - Output parsers. - Tools. - Document loaders. - Text

``` text

   |

   |
Output parser
   |
Answer
```

Use LangChain when you need reusable components and integrations to
connect models, prompts, retrievers and tools.

## 3.8 LangGraph

LangGraph is a framework for building stateful, multi-step graph
workflows, including agent workflows.

Core concepts:

**State:** data shared across graph execution, such as user input,
retrieved documents, tool results and current messages.

**Node:** a function or operation that reads state and returns updates.

**Edge:** defines which node runs next.

**Conditional edge:** chooses the next node based on state or a
condition.

**Cycle/loop:** allows a workflow to repeat a step, such as asking a
model to decide whether another tool call is required.

**Checkpointing:** saving workflow state at points in execution so a
process can be resumed or inspected, depending on configuration and
persistence setup.

Conceptual graph:

``` text
START
  |
  v
Agent node
  |
  v
Needs tool?
  | yes             | no
  v                 v
Tool node          END
  |
  v
Agent node
```

**Q: LangChain vs LangGraph?**\
A: LangChain provides components and integrations for building LLM
applications. LangGraph focuses on orchestrating stateful workflows as
graphs with nodes, edges, conditional routing and cycles. They can be
used together.

**Q: What are nodes and edges?**\
A: Nodes perform operations; edges determine the flow between
operations.

**Q: What is state?**\
A: State is the structured information carried through workflow
execution. Nodes read relevant state and return updates.

## 3.9 Multi-agent systems

A multi-agent system uses multiple agents, often with different roles,
to work on a task.

Example: - Research agent gathers information. - Analysis agent
interprets it. - Report agent creates a report.

``` text
             User task
                 |
                 v
            Supervisor
            /    |    \
           v     v     v
       Research Analysis Report
         agent    agent  agent
```

Possible communication patterns:

1.  **Shared state:** agents read and update a common workflow state.
2.  **Message passing:** one agent sends a structured result/message to
    another.
3.  **Supervisor pattern:** a coordinator chooses which agent acts next.
4.  **Sequential pipeline:** output from one agent becomes input to the
    next.

**Q: Do multiple agents always improve quality?**\
A: No. They add latency, cost, complexity and failure points. A single
model call or deterministic workflow may be better for simple tasks. Use
multiple agents only when task separation or coordination provides a
real benefit.

**Q: How do agents communicate?**\
A: Through structured state or messages managed by the orchestration
layer. Define clear input/output schemas so each agent knows what it
receives and returns.

**Q: How do you stop an infinite agent loop?**\
A: Set maximum graph steps/iterations, tool-call limits, timeouts,
budgets and explicit stop conditions. Log the reason for termination.

## 3.10 Agent memory

Memory is information made available to an agent beyond the immediate
prompt.

-   Short-term/session memory: current conversation or workflow state.
-   Long-term memory: information stored across sessions, subject to
    user consent, retention and access rules.

Memory may be stored in a database, conversation store or retrieval
system. Do not assume every agent framework automatically gives
persistent memory.

**Q: Is conversation history the same as long-term memory?**\
A: Not necessarily. Conversation history is a record of messages.
Long-term memory usually involves selecting, storing and retrieving
relevant information across sessions.

## 3.11 Human-in-the-loop (HITL)

Human-in-the-loop means pausing an automated workflow for human review
or approval.

Example:

``` text
Agent prepares a payment request
             |
             v
       Approval checkpoint
          /       \
      Approve     Reject
        |           |
        v           v
    Execute       Stop
```

Use it for sensitive actions such as payments, deleting data, sending
external communications or changing permissions.

**Q: Why is HITL useful?**\
A: It provides oversight for high-impact actions, allows humans to
correct mistakes and reduces the risk of uncontrolled automation.

## 3.12 Monitoring agents

Your resume mentions tracking token usage, execution latency and API
costs.

-   Token usage: number of input and output tokens consumed.
-   Latency: time taken for a request or workflow.
-   Cost: estimated provider charge based on model pricing and token
    usage.
-   Success/failure rate: percentage of executions that complete
    successfully.
-   Tool error rate: how often external tools fail.
-   Trace: a record of the steps taken during an execution.

Useful monitoring fields: - workflow ID - execution ID - agent/node
name - start and end time - model/provider - token counts - tool name -
status - error category - cost estimate

Never log API keys, passwords, full sensitive prompts or personal data
without a justified and protected logging design.

## 3.13 Why MongoDB and Redis?

**MongoDB:** can store users, workflow definitions, configuration,
execution history and structured documents, depending on the schema.

**Redis:** an in-memory data store often used for caching, rate
limiting, short-lived state, queues or coordination.

**Q: Why use Redis if MongoDB already stores data?**\
A: They serve different roles. MongoDB is commonly used for durable
application data. Redis is useful for fast, short-lived or
coordination-oriented data. Redis should not be described as a
replacement for durable storage unless the system is explicitly designed
for that.

Example conceptual workflow:

## 4.2 What is a deepfake?

A deepfake is synthetic or manipulated media in which a person's face,
voice or other content is altered or generated using AI techniques.

Potential risks include impersonation, misinformation, fraud and
reputational harm.

Detection is difficult because: - Manipulation methods change. -
Compression can remove useful visual clues. - Training data may not
represent real-world media. - A model may learn dataset-specific
artifacts rather than general manipulation features.

## 4.3 Machine learning vs deep learning

**Machine learning:** algorithms learn patterns from data.

**Deep learning:** a subset of ML using multi-layer neural networks to
learn representations.

Traditional ML may rely more on manually designed features. Deep
learning can learn useful features from data, but requires careful data,
training and evaluation.

## 4.4 What is a neural network?

A neural network is a model made of connected computational units
arranged in layers. It applies learned weights and nonlinear
transformations to input data to produce an output.

Typical training loop: 1. Feed input data forward. 2. Calculate
prediction. 3. Compare prediction with the true label using a loss
function. 4. Backpropagate gradients. 5. Update weights using an
optimizer. 6. Repeat over batches and epochs.

**Epoch:** one pass through the training dataset.\
**Batch size:** number of examples processed in one training step.\
**Loss:** numerical measure of prediction error.\
**Optimizer:** algorithm that updates model parameters.\
**Learning rate:** controls update size.

## 4.5 What is a CNN?

CNN means Convolutional Neural Network.

CNNs are widely used for image processing. Convolution filters learn
local patterns such as edges, textures and shapes. Deeper layers can
combine these into more complex features.

Common components: - Convolution layer: applies learned filters. -
Activation function: adds non-linearity, commonly ReLU. - Pooling:
reduces spatial dimensions. - Fully connected layer: combines learned
features for prediction. - Output layer: produces class scores or
probabilities.

**Q: Why use CNN for image detection?**\
A: CNNs are effective at learning spatial/local visual features from
images, such as texture and facial-region patterns.

## 4.6 What is a Transformer?

A Transformer is a neural-network architecture built around attention
mechanisms.

Self-attention lets the model represent relationships between different
tokens or input positions. For images, an image can be split into
patches that are represented as tokens.

**Q: What is attention?**\
A: Attention computes how strongly one part of the input should relate
to other parts when forming a representation. In self-attention, the
input elements interact with one another.

**Q: Why use Transformers?**\
A: They can model long-range relationships and global context. They can
complement local visual features learned by CNNs.

## 4.10 Evaluation metrics

For binary classification:

-   True Positive (TP): manipulated media correctly identified as
    manipulated.
-   True Negative (TN): authentic media correctly identified as
    authentic.
-   False Positive (FP): authentic media incorrectly flagged as
    manipulated.
-   False Negative (FN): manipulated media missed by the detector.

**Accuracy**

`(TP + TN) / (TP + TN + FP + FN)`

**Precision**

`TP / (TP + FP)`

Of all items predicted manipulated, how many really were manipulated?

**Recall**

`TP / (TP + FN)`

Of all manipulated items, how many did the model detect?

**F1-score**

`2 × Precision × Recall / (Precision + Recall)`

F1 balances precision and recall.

**Q: Why is accuracy alone insufficient?**\
A: If the dataset is imbalanced, a model can achieve high accuracy by
favouring the majority class. Precision, recall, F1 and a confusion
matrix provide a fuller view.

**Q: What is overfitting?**\
A: A model performs well on training data but poorly on unseen data
because it has learned training-specific patterns.

**Q: How do you reduce overfitting?**\
A: Use suitable data augmentation, regularization, early stopping,
sufficient diverse training data and proper validation. Avoid leakage
between train and test sets.

**Q: What is data leakage?**\
A: Information from the test/validation set improperly influences
training or model selection, leading to overly optimistic evaluation.

**Q: What is generalization?**\
A: The ability to perform well on unseen data, including data from
different sources or manipulation methods.

## 5.1 var, let and const

-   `var`: function-scoped; can be redeclared; hoisted and initialized
    as `undefined`.
-   `let`: block-scoped; cannot be redeclared in the same scope; has a
    temporal dead zone before initialization.
-   `const`: block-scoped; must be initialized; cannot be reassigned,
    but objects/arrays it references can still be mutated.

``` javascript

count = 2;

const user = { name: "Yashas" };
user.name = "Sam"; // allowed
// user = {};      // not allowed
```

## 5.2 == vs ===

`==` performs type coercion in many comparisons.\
`===` compares without type coercion.

Prefer `===` unless you intentionally need coercion.

## 5.3 Primitive vs reference types

Primitive values include string, number, bigint, boolean, undefined,
symbol and null.

Objects, arrays and functions are reference types. Assigning an object
variable copies the reference, not a deep copy of the object.

## 5.4 Hoisting

Declarations are processed before code execution, but their behaviour
differs: - `var` declarations are hoisted and initialized to
`undefined`. - `let` and `const` are hoisted but cannot be accessed
before initialization due to the temporal dead zone. - Function
declarations can be called before their definition in the same scope.

## 5.5 Closure

A closure occurs when a function retains access to variables from its
lexical scope even after the outer function has finished executing.

``` javascript
function makeCounter() {
  let count = 0;

  return function () {
    count++;
    return count;
  };
}

const counter = makeCounter();
console.log(counter()); // 1
console.log(counter()); // 2
```

The returned function retains access to `count`.

## 5.6 Callback, Promise and async/await

**Callback:** a function passed to another function to be called later.

**Promise:** an object representing the eventual completion or failure
of an asynchronous operation.

Promise states: pending, fulfilled, rejected.

**async/await:** syntax that makes Promise-based asynchronous code
easier to read. An `async` function always returns a Promise.

``` javascript
async function getUser() {
  try {
    const response = await fetch("/api/user");
    if (!response.ok) {
      throw new Error("Request failed");
    }
    return await response.json();
  } catch (error) {
    console.error(error);
    throw error;
  }
}
```

## 5.7 Event loop

JavaScript commonly runs user code on a single main thread in a runtime.
The event loop coordinates execution of synchronous code, queued
callbacks and asynchronous tasks.

Important: - Call stack: currently executing functions. - Task/macrotask
queue: tasks such as timers and some I/O callbacks. - Microtask queue:
Promise reactions and `queueMicrotask`. - Microtasks are generally
processed after the current synchronous work and before the next task.

**Q: Is Node.js single-threaded?**\
A: JavaScript callbacks usually execute on the main event-loop thread,
but Node.js also uses operating-system asynchronous facilities and a
libuv thread pool for certain operations. Worker threads can run
JavaScript in parallel. "Node.js is single-threaded" is an
oversimplification.

## 5.8 map, filter and reduce

``` javascript
const nums = [1, 2, 3, 4];

const doubled = nums.map(n => n * 2);       // [2, 4, 6, 8]
const evens = nums.filter(n => n % 2 === 0); // [2, 4]
const sum = nums.reduce((a, n) => a + n, 0); // 10
```

-   `map`: transforms each element.
-   `filter`: keeps elements matching a condition.
-   `reduce`: accumulates values into one result.

## 5.9 Shallow copy vs deep copy

A shallow copy duplicates only the outer object; nested objects remain
shared references.

A deep copy duplicates nested structures too. `structuredClone()` works
for many supported data types, but not every possible value.

## 5.10 TypeScript

TypeScript is a typed superset of JavaScript that adds a static type

# 8. Databases: MongoDB, PostgreSQL and Redis

## 8.1 PostgreSQL

PostgreSQL is an open-source relational database. It stores structured
data in tables and supports SQL, transactions, constraints, indexes and
advanced data types.

**Q: Primary key?**\
A: A column or set of columns that uniquely identifies each row and
cannot be NULL.

**Q: Foreign key?**\
A: A constraint that enforces a relationship to a key in another table
(or the same table).

**Q: Normalization?**\
A: Organizing relational data to reduce unwanted duplication and update
anomalies.

-   1NF: columns contain atomic values under the chosen relational
    model; no repeating groups.
-   2NF: in 1NF and non-key attributes depend on the whole candidate
    key, not just part of a composite key.
-   3NF: in 2NF and non-key attributes do not depend transitively on
    candidate keys (informally).
-   BCNF: every determinant is a candidate key.

## 8.2 SQL joins

-   INNER JOIN: rows with matching join keys on both sides.
-   LEFT JOIN: all left-side rows plus matching right-side rows;
    unmatched right values become NULL.
-   RIGHT JOIN: all right-side rows plus matching left-side rows.
-   FULL OUTER JOIN: all rows from both sides, matched where possible.

Example:

``` sql
SELECT e.name, d.department_name
FROM employees e
INNER JOIN departments d
  ON e.department_id = d.id;
```

## 8.3 GROUP BY and HAVING

`GROUP BY` groups rows for aggregation. `HAVING` filters groups after
aggregation. `WHERE` filters rows before grouping.

``` sql
SELECT department_id, COUNT(*) AS employee_count
FROM employees
WHERE status = 'active'
GROUP BY department_id
HAVING COUNT(*) > 5;
```

``` sql
SELECT MAX(salary) AS second_highest_salary
```

**Q: What is caching?**\

## 9.1 Complexity basics

-   O(1): constant.
-   O(log n): logarithmic, e.g. binary search on sorted data.
-   O(n): linear.
-   O(n log n): common efficient comparison sorts.
-   O(n²): nested full scans over n items.

Space complexity describes additional memory used, with conventions

## 9.2 Arrays and strings

### Two Sum

**Problem:** Find two indices whose values add to target.

Approach: store previously seen values in a hash map. For each number
`x`, check whether `target - x` has already appeared.

``` cpp
vector<int> twoSum(vector<int>& nums, int target) {
    unordered_map<int, int> seen;

    for (int i = 0; i < (int)nums.size(); i++) {
        int need = target - nums[i];
        if (seen.count(need)) {
            return {seen[need], i};
        }
        seen[nums[i]] = i;
    }
    return {};
}
```

Time: O(n) average. Extra space: O(n).

### Valid palindrome

Use two pointers from both ends, skipping characters that are not
relevant if the problem specifies that rule. Compare normalized
characters.

Time: O(n). Extra space: O(1) if processed in place/on the fly.

### Maximum subarray (Kadane's algorithm)

Maintain the best subarray ending at the current position and the global
best.

``` cpp
int maxSubArray(vector<int>& nums) {
    int current = nums[0], best = nums[0];

    for (int i = 1; i < (int)nums.size(); i++) {
        current = max(nums[i], current + nums[i]);
        best = max(best, current);
    }
    return best;
}
```

Time: O(n), extra space O(1).

### Best time to buy and sell stock (one transaction)

Track the minimum price so far and the best profit from selling today.

``` cpp
int maxProfit(vector<int>& prices) {
    int minimum = INT_MAX;
    int best = 0;

    for (int price : prices) {
        minimum = min(minimum, price);
        best = max(best, price - minimum);
    }
    return best;
}
```

Time: O(n), extra space O(1).

### Move zeroes

Use a write pointer for the next non-zero position. Move non-zero
elements forward, then fill remaining positions with zeroes.

Time: O(n), extra space O(1).

## 9.3 Binary search

Binary search requires a sorted search space or another monotonic
condition.

``` cpp
int binarySearch(vector<int>& a, int target) {
    int low = 0, high = (int)a.size() - 1;

    while (low <= high) {
        int mid = low + (high - low) / 2;

        if (a[mid] == target) return mid;
        if (a[mid] < target) low = mid + 1;
        else high = mid - 1;
    }
    return -1;
}
```

Time: O(log n), extra space O(1).

Common follow-ups: - First occurrence. - Last occurrence. - Lower
bound. - Upper bound. - Search in rotated sorted array. - Binary search
on answer.

## 9.4 Stack --- Valid Parentheses

Use a stack. Push opening brackets. For each closing bracket, check that
the top has the matching opening bracket. At the end, the stack must be
empty.

Time: O(n), space: O(n).

## 9.5 Linked lists

**Reverse linked list:** iterate through nodes and redirect `next`
pointers using `prev`, `curr` and `nextNode`. Time O(n), extra space
O(1).

**Detect cycle:** Floyd's tortoise-and-hare algorithm uses slow and fast
pointers. If they meet, a cycle exists. Time O(n), space O(1).

**Merge two sorted linked lists:** use a dummy node and repeatedly
attach the smaller current node. Time O(n + m), extra space O(1)
excluding output nodes.

## 9.6 Trees

**Maximum depth:** recursively compute `1 + max(leftDepth, rightDepth)`.
Time O(n); recursion stack O(h), where h is tree height.

**Level-order traversal:** use a queue and process nodes breadth-first.
Time O(n), space O(w), where w is maximum tree width.

## 9.7 Dynamic programming

Dynamic programming is useful when a problem has overlapping subproblems
and optimal substructure.

**Climbing stairs:** ways to reach step n = ways(n-1) + ways(n-2), with
appropriate base cases.

``` cpp
int climbStairs(int n) {
    if (n <= 2) return n;

    int a = 1, b = 2;
    for (int i = 3; i <= n; i++) {
        int c = a + b;
        a = b;
        b = c;
    }
    return b;
}
```

Time O(n), space O(1).

## 10.1 Class and object

## 10.2 Four pillars

**Abstraction:** expose essential behaviour while hiding implementation

**Inheritance:** derive a class from another class to reuse/extend

## 10.3 Overloading vs overriding

## 10.4 Interface vs abstract class

operations. Exact language features differ.

## 10.5 Composition vs inheritance

Composition builds a type using other objects ("has-a"). Inheritance
models a subtype ("is-a"). Prefer composition when it gives clearer,
less tightly coupled designs.

## 10.6 Stack vs heap

Stack memory commonly holds function-call frames and local execution
data. Heap memory is used for dynamically allocated objects. Actual
allocation and optimization details depend on the language/runtime.

# 11. Operating Systems

## 11.1 Process vs thread

-   Process: a running program with its own virtual address space and
    resources.
-   Thread: an execution path within a process. Threads in one process
    share process memory/resources but have their own stacks and
    execution state.

## 11.2 Context switching

The OS saves the state of one running task and restores another so the
CPU can switch execution. It has overhead.

## 11.3 Concurrency vs parallelism

-   Concurrency: multiple tasks make progress during overlapping
    periods.
-   Parallelism: multiple tasks execute at the same instant on different
    processing resources.

## 11.4 Deadlock

A deadlock occurs when processes/threads wait indefinitely for resources
held by each other.

Four Coffman conditions: 1. Mutual exclusion. 2. Hold and wait. 3. No
preemption. 4. Circular wait.

All four are necessary for the classic deadlock conditions.

## 11.5 Mutex vs semaphore

-   Mutex: lock used to provide exclusive access to a critical section.
-   Semaphore: counter-based synchronization primitive that can allow a
    limited number of concurrent accesses.

## 11.6 Virtual memory and paging

Virtual memory gives each process an address space that the OS and
hardware map to physical memory. Paging divides virtual and physical
memory into fixed-size pages/frames.

## 11.7 Scheduling

CPU scheduling decides which ready task gets CPU time. Common algorithms
include FCFS, shortest-job-first, priority scheduling and round-robin.
Each has trade-offs in fairness, waiting time and response time.

# 12. Computer Networks

## 12.1 OSI model

  Layer   Name           Example responsibility
  ------- -------------- -----------------------------------------
  7       Application    Application protocols
  6       Presentation   Data representation/encryption concepts
  5       Session        Session management concepts
  4       Transport      End-to-end transport (TCP/UDP)
  3       Network        Routing and IP addressing
  2       Data Link      Local link delivery, frames
  1       Physical       Bits/signals over medium

The Internet protocol suite is commonly explained using fewer layers;
OSI is a conceptual reference model.

## 12.2 TCP vs UDP

  -----------------------------------------------------------------------
  TCP                                 UDP
  ----------------------------------- -----------------------------------
  Connection-oriented                 Connectionless

  Reliable ordered byte stream        Datagram delivery without built-in
                                      reliability

  Retransmission and flow/congestion  Lower protocol overhead
  control                             

  Used by HTTP/1.1 and HTTP/2 in      Used by DNS in many cases,
  common deployments                  streaming/real-time protocols and
                                      QUIC transport
  -----------------------------------------------------------------------

Do not say UDP is always faster in every real-world situation. It offers
different guarantees and leaves reliability/application behaviour to
higher layers.

## 12.3 HTTP vs HTTPS

HTTPS is HTTP protected by TLS. TLS provides encryption, integrity
protection and server authentication (and optionally client
authentication).

## 12.4 DNS

DNS translates domain names into records such as IP addresses. A
resolver may consult caches and DNS servers to find the required record.

## 12.5 What happens when you enter a URL in a browser?

A simplified flow: 1. Browser parses the URL. 2. Browser checks relevant
caches. 3. DNS resolution finds an IP address. 4. Browser establishes a
transport connection (TCP, or QUIC for HTTP/3). 5. TLS negotiation
occurs for HTTPS. 6. Browser sends an HTTP request. 7. Server/load
balancer/application processes it. 8. Server returns an HTTP response.
9. Browser parses HTML, fetches resources and renders the page.

## 12.6 TCP three-way handshake

1.  Client sends SYN.
2.  Server replies SYN-ACK.
3.  Client sends ACK.

This establishes a TCP connection.

## 12.7 IP address vs port

An IP address identifies a network interface/host for routing. A port
identifies an application endpoint on that host. Together they help
identify a network communication endpoint.

# 13. System design fundamentals for a fresher

You are not expected to design a huge distributed system in one day, but
understand the basic building blocks.

## 13.1 Client-server architecture

The client sends a request; the server processes it and returns a
response.

## 13.2 Load balancer

A load balancer distributes incoming traffic across multiple backend
instances. It can improve availability and scale, depending on
configuration.

## 13.3 Horizontal vs vertical scaling

-   Vertical: increase resources on one machine.
-   Horizontal: add more machines/instances.

## 13.4 Cache

A cache stores frequently accessed data for faster retrieval. Know cache
hit, cache miss, TTL and invalidation.

## 13.5 Message queue

A message queue allows producers to send work that consumers process
asynchronously. It can decouple services and smooth traffic spikes.

## 13.6 Database replication

Replication copies data from one database node to another. It can
improve read scalability and availability, but introduces consistency
and failover considerations.

## 13.7 SQL vs NoSQL in system design

Choose based on data relationships, query patterns, consistency
requirements, scaling needs and operational complexity. Do not choose
solely based on popularity.

# 14. Go fundamentals (because Go is listed on your resume)

Only claim the level you can demonstrate.

## 14.1 What is Go?

Go is a statically typed, compiled programming language designed for
simplicity, performance and practical concurrent programming.

## 14.2 Struct

A struct groups fields into a composite type.

``` go
type User struct {
    ID   int
    Name string
}
```

## 14.3 Methods and receivers

A method is a function associated with a receiver type.

``` go
func (u User) Greet() string {
    return "Hello " + u.Name
}
```

A value receiver receives a copy of the value. A pointer receiver can
modify the original value and can avoid copying larger structs.

## 14.4 Interfaces

An interface specifies a set of method behaviours. A type satisfies an
interface implicitly by implementing its methods.

``` go
type Speaker interface {
    Speak() string
}

type Person struct{}

func (Person) Speak() string {
    return "Hello"
}
```

## 14.5 Error handling

Go commonly returns errors as values.

``` go
value, err := doWork()
if err != nil {
    return err
}
```

The caller checks and handles the error explicitly.

## 14.6 Goroutines and channels

A goroutine is a lightweight concurrent execution unit managed by the Go
runtime.

A channel allows goroutines to communicate and synchronize by sending
and receiving values.

``` go
ch := make(chan int)

go func() {
    ch <- 42
}()

value := <-ch
```

## 14.7 Mutex

A mutex protects shared mutable data from concurrent access.

``` go
var mu sync.Mutex
mu.Lock()
// access shared state
mu.Unlock()
```

Use `defer mu.Unlock()` after locking in normal function patterns where
appropriate.

# 15. Testing, debugging and Git

## 15.1 Unit vs integration testing

-   Unit test: tests a small unit, often with dependencies isolated.
-   Integration test: checks whether multiple components work together.
-   End-to-end test: tests a user-visible workflow through the system.

## 15.2 API testing

Test: - Successful request. - Missing/invalid fields. - Unauthorized
request. - Forbidden resource access. - Resource not found. - Duplicate
request. - Database failure. - Boundary values.

Postman can be used to manually send HTTP requests and inspect
responses. Automated API tests should also be considered.

## 15.3 Debugging answer

**Q: How do you debug a backend issue?**\
A: "I first reproduce the issue, inspect the request and response, read
the server logs, identify the failing layer, isolate the cause, create a
fix, and test both the original failure and related edge cases. I avoid
hiding errors with broad catch blocks."

## 15.4 Git basics

-   `git clone`: copy a remote repository.
-   `git status`: inspect working tree.
-   `git add`: stage changes.
-   `git commit`: record staged changes.
-   `git push`: send commits to remote.
-   `git pull`: fetch and integrate remote changes.
-   `git branch`: inspect/create branches.
-   `git merge`: integrate branch changes.
-   `git rebase`: replay commits on another base.

**Q: Merge vs rebase?**\
A: Merge combines histories and can create a merge commit. Rebase
replays commits on a new base and creates new commit IDs. Avoid rebasing
shared published history unless the team agrees.

# 16. High-probability project questions --- quick answer bank

## MonetaBank

**1. Why React?**\
Reusable components and state-driven UI make it suitable for building an
interactive dashboard.

**2. Why Express?**\
It provides lightweight routing and middleware for Node.js APIs.

**3. Why MongoDB?**\
It provides document storage and flexible schemas. Explain the actual

constraints might make PostgreSQL a better fit.

**4. Why JWT?**\
It is a signed token format that can carry identity/authorization claims
between requests. It must be verified and paired with sound expiry,
storage and authorization practices.

**5. How do you protect account data?**\
Authenticate the user, authorize access to the specific account on the
server, validate inputs, avoid trusting client-supplied ownership IDs
and log security-relevant events safely.

## Agentic AI

**1. Why use an LLM?**\
To interpret natural-language instructions and generate
context-sensitive responses or action plans.

**2. Why RAG?**\
To retrieve relevant external/private information and supply it as
context to the model.

**3. Why LangGraph?**\
To orchestrate multi-step, stateful workflows with conditional
transitions and cycles.

**4. Why Redis?**\
For suitable fast, short-lived or coordination-related data such as
caching or rate limiting, depending on the actual design.

**5. Why multiple agents?**\
To separate specialized responsibilities when coordination provides
value. It is not always necessary.

## DeepGuard

**1. Why CNN?**\
For learning local spatial patterns in images.

**2. Why Transformer?**\
For modelling broader relationships using attention.

**3. Why FaceForensics++?**\
It is a public benchmark dataset containing real and manipulated facial
videos for research and evaluation.

**4. Why F1-score?**\
It combines precision and recall, useful when both false positives and
false negatives matter.

**5. Main limitation?**\
Generalization to unseen manipulation techniques, compression and
real-world media is difficult; evaluation must use appropriate unseen
data.
